# Setting up MongoDB Atlas (the missing database)

Last verified: **2 October 2026**

This is the blocker for deploying the backend. Render is currently pointed at a
MongoDB Atlas cluster that no longer exists.

---

## The error, and what it means

When deploying on Render you will see:

```
MongoDB connection error: Error: querySrv ENOTFOUND
_mongodb._tcp.scatch-prod.ciaaonh.mongodb.net
  errno: undefined, code: 'ENOTFOUND', syscall: 'querySrv'
```

`ENOTFOUND` is a **DNS** failure, not a password or permissions failure. It means
the hostname `scatch-prod.ciaaonh.mongodb.net` does not resolve at all — that
cluster was deleted. No amount of changing the username or password will fix
this, because there is no server to authenticate against.

Confirmed:

```bash
$ host scatch-prod.ciaaonh.mongodb.net
Host scatch-prod.ciaaonh.mongodb.net not found: 3(NXDOMAIN)
```

Because the DNS lookup fails instantly, the app *appears* responsive — requests
come back in ~0.3s with `{"success":false}` instead of hanging. That is a fast
failure dressed up as a healthy one, which is why it is easy to mistake for an
empty database. It is not empty. It is unreachable.

### The other two lines in that error are harmless

| Message | Verdict |
|---|---|
| `useUnifiedTopology is a deprecated option` | Comes from the old Mongoose/MongoDB driver. Disappears once the new code is deployed — the new code does not pass that option. |
| `NODE_ENV value of 'production' did not match any deployment config file names` | A dependency warning looking for a file literally named `production.js`. There is no such file and there should not be. Ignore it. |

Neither is why the deploy failed. Only `ENOTFOUND` matters.

## What you need first

An Atlas account and a free cluster. The free **M0** tier is enough — it never
expires on a trial basis and is fine for a demo or a student project. It gives
you a shared 512 MB, which is plenty for this app.

---

## Step 1 — Create the cluster

1. Go to <https://cloud.mongodb.com> and sign in.
2. If prompted, choose a region **near you**. Region cannot be changed later
   without a migration, so pick sensibly (Mumbai `ap-south-1` if you're in
   India).
3. Click **Create Deployment** (sometimes labelled *Create Cluster*).
4. Leave the tier as **M0 / Free**. No payment details are required for M0.
5. Take the default cluster name, or use `scatch`. Click **Create Deployment**.
6. Wait 1–3 minutes while the cluster provisions.

---

## Step 2 — Create a database user

This is the username and password you will put in the connection string. They
are **not** your Atlas login credentials.

1. In the left sidebar, click **Database Access** (under *Deployment*).
2. Click **Add New Database User**.
3. Authentication method: **Password**.
4. Username: `scatchapp` (anything you like).
5. Password: **Autogenerate Secure Password** — copy it into a password manager
   now. Once you leave this screen you cannot read it again.

> If you use a manual password, Atlas rejects passwords shorter than 8
> characters, and it must not contain `/ : " ? < > |` or spaces. Prefer the
> autogenerated one — it is longer and has no awkward characters to escape when
> it lands in a URL.

6. Database User Privileges: **Read and write to any database**.
7. Click **Add User**.

---

## Step 3 — Allow Render to connect

Atlas blocks every IP by default. If you skip this step, the connection fails
with a **timeout** rather than `ENOTFOUND` — a different error, so if you see
that, come back here.

1. Left sidebar → **Network Access** (under *Deployment*).
2. Click **Add IP Address**.
3. Enter `0.0.0.0/0` — this allows any IP.

### Why allow the whole internet?

Render does not give your service a fixed outbound IP address, so there is no
single address to allow. The alternatives are:

| Option | Trade-off |
|---|---|
| `0.0.0.0/0` (allow all) | Works immediately. Your database is still protected by username + password and lives on a private network that Atlas does not expose publicly. This is what almost every Render deployment does. |
| Render's published AWS egress ranges | Narrower, but Render does not publish a stable list, so this tends to break later without warning. |
| Static outbound IP (paid Render plan) | Best security. Only possible on a paid instance type. |

Given this is a student/demo project, `0.0.0.0/0` with a strong autogenerated
password is a reasonable trade-off. The database is never directly reachable
over HTTP — MongoDB speaks its own protocol on a non-standard port.

---

## Step 4 — Copy the connection string

1. Left sidebar → **Database** (under *Deployment*).
2. Click **Connect** on your cluster.
3. Choose **Drivers**.
4. Choose **Node.js** as the driver. The version dropdown does not matter.
5. Copy the string. It looks like this, with a `<db_password>` placeholder:

```
mongodb+srv://scatchapp:<db_password>@scatch.<random>.mongodb.net/?retryWrites=true&w=majority
```

6. **Replace `<db_password>` with the password from Step 2.**

### The one thing people get wrong

If your password contains special characters, they must be percent-encoded, or
the driver misreads the string. Safest fix: use Atlas's **Autogenerated Secure
Password**, which is alphanumeric and needs no escaping. If you picked your own
with a `@ : / ? # [ ] %`, encode them — `@` becomes `%40`, `/` becomes `%2F`,
and so on.

Also confirm the host matches your cluster name. If you named the cluster
`scatch` the host starts `scatch.`, not `scatch-prod.`.

---

## Step 5 — Put it on Render

1. Render dashboard → your `scatch-website` web service.
2. **Environment** in the sidebar.
3. Find `MONGODB_URI` and set it to your new connection string:

   ```
   mongodb+srv://scatchapp:YOUR_REAL_PASSWORD@scatch.xxxxx.mongodb.net/?retryWrites=true&w=majority
   ```

4. Confirm the rest of the environment while you are there:

   | Variable | Value |
   |---|---|
   | `MONGODB_URI` | your new connection string |
   | `JWT_KEY` | a long random string (see below) |
   | `CLIENT_URL` | `https://scatch-website.vercel.app` |
   | `CLOUDINARY_CLOUD_NAME` | `dunxugggm` |
   | `CLOUDINARY_API_KEY` | from the Cloudinary dashboard |
   | `CLOUDINARY_API_SECRET` | from the Cloudinary dashboard |

   For `JWT_KEY`, generate one with:

   ```bash
   node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"
   ```

5. Click **Save Changes**.

> `MONGODB_URI` must be non-empty. The server deliberately refuses to start in
> production without it, rather than silently running an empty in-memory store
> and pretending everything is fine. That is exactly the class of confusion this
> whole situation caused.

6. **Manual Deploy → Deploy latest commit.**

## Step 6 — Seed the database

A fresh cluster has no users, products or orders, so the app will have nothing
to show and no way to log in.

From the repo:

```bash
cd server
# make sure server/.env has MONGODB_URI set to your NEW cluster first
npm run seed
```

This creates 2 sellers, 2 customers, 6 products and ~24 orders spread over 6
months so the seller analytics charts have real data. Every demo account uses
the password `Password123`:

| Role     | Email                |
|----------|----------------------|
| Customer | `user@scatch.dev`    |
| Customer | `user2@scatch.dev`   |
| Seller   | `seller@scatch.dev`  |
| Seller   | `seller2@scatch.dev` |

Sellers log in at `/seller/login`, customers at `/user/login`. They are separate
account types and cannot be interchanged — a seller login at `/user/login`
returns `{"success":false}` with no message, which looks like a wrong password.

---

## Step 7 — Verify

All four must pass.

```bash
# 1. backend is up and talking to MongoDB
curl -i https://scatch-website.onrender.com/api/health
#    expect 200 with JSON

# 2. backend runs the current code, not the old build
curl -X POST -H 'Content-Type: application/json' -d '{}' \
  https://scatch-website.onrender.com/api/definitely-not-a-route
#    expect {"success":false,"error":"Endpoint not found"}
#    HTML "Cannot POST" means the old code is still live

# 3. data is actually there now
curl -s https://scatch-website.onrender.com/api/product/products
#    expect a JSON list of products, not {"success":false}

# 4. images
curl -o /dev/null -w '%{http_code}\n' \
  https://res.cloudinary.com/dunxugggm/image/upload/samples/ecommerce/shoes
#    expect 200
```

Then in a browser: log in at `https://scatch-website.vercel.app/user/login` with
`user@scatch.dev` / `Password123`, browse the shop, and open My Orders.

## Troubleshooting

| Error | Meaning | Fix |
|---|---|---|
| `querySrv ENOTFOUND` | Hostname does not exist | Wrong or deleted cluster. Copy the string fresh from Atlas → Connect → Drivers. |
| `Server selection timed out after 30000 ms` | DNS fine, connection blocked | Network Access allowlist. Add `0.0.0.0/0`. |
| `Authentication failed` | Credentials wrong | Check the username exists in Database Access. If the password has `@ : / ?` it must be percent-encoded. |
| `MongoServerError: bad auth` on Atlas free tier | Same as above | Retry the password — copy it with the "Edit User" → "Autogenerate Secure Password" flow if unsure. |
| `MONGODB_URI is required in production` | Variable empty or unset | Set it on Render and confirm you clicked **Save Changes**, not just edited the field. |
| Everything returns `{"success":false}` in ~0.3s | Queries are failing and being swallowed | Look in the Render **Logs** for the real error. It is being hidden by a `catch` block. |
| Images show grey "No image" | Cloudinary id wrong or unreachable | Use the *full* public id including folder, e.g. `samples/ecommerce/shoes`. Partial ids 404. |

Always read the **Render deploy log** for the underlying error — the app's
`{"success":false}` responses hide the real cause, which is what made this
diagnosis slow.

## Cost and limits

M0 free tier:

- 512 MB storage, shared
- No credit card required
- Sleeps after inactivity in some configurations (Atlas itself does not sleep;
  Render's free *web service* does, so the first request after idle can take
  ~50s while it wakes)

If you outgrow it, M2 ($9/month) gives a dedicated cluster and no sleeping. Not
needed for this project.

## Do not commit any of this

The connection string contains a password. It belongs in Render's environment
variables and in your local untracked `server/.env` — never in a file that gets
committed. `server/.env` and `client/.env` are both gitignored, and
`.env.example` is the committed template with placeholders only.

This repo is **public**. Anyone with the URL can read every commit, forever.
